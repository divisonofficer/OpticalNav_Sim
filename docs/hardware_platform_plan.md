바닥(거칠기 0.35) 0.60. 값마다 근거가 함께 기록되고 재질·영역 단위로 덮어쓸 수 있다. **광학 거칠기는 마찰 측정값이 아니다**: 근거 있는
기본값일 뿐이다.

동역학 검증: 제동 거리 0.084 / 0.254 / 0.510 m(μ 0.6 / 0.2 / 0.1, v₀ = 1 m/s. v₀²/2μg 대비 1.5% 이내). μ 0.05에서 급출발 0.5초 뒤
0.245 m/s(= μgt), 바퀴는 1 m/s로 헛돌아 오도메트리 0.47 m, 실제 0.06 m. 좌우 μ 0.1 / 0.8에서 제동하면 마찰 큰 쪽으로 6° 회전. 마찰이
충분하면 4 m 주행 뒤 운동학 모델과 4 cm 차이. 한계를 넘는 선회에서는 구심 가속도가 μg를 넘지 않는다(4륜 조향이라 "바깥으로 밀림"이
아니라 속도가 떨어지며 다른 원을 그린다: 처음 세운 검증 문구가 틀렸다).

로봇 수치는 제조사 매뉴얼(RANGER MINI 2.0 User Manual V2.0.1, 2023.08)로 바꿨다: 공차중량 64.5 kg, 최대 적재 80 kg, 구동 모터 350 W × 4,
최고 속도 1.5 m/s(조향 20° 초과 시 0.75 m/s), 제자리 회전 3.259 rad/s, Ackermann 조향 명령은 안쪽 바퀴 각도이고 최대 0.698 rad(40°).
이 각도에서 차체 바깥 모서리의 회전 반경이 0.814 m로, 매뉴얼의 최소 회전 반경 810 mm와 맞는다. 매뉴얼에 없는 값(가속 한계, 조향
속도, 바퀴 관성, 타이어 특성, 리그 무게 12 kg)은 여전히 추정이다.

### M4a 광선 조회
- 서버에는 이미 픽셀별 방향 표로 광선을 쏘는 깊이 렌더(`Resident.depth_image`)가 있다. 같은 방식으로 임의의 광선 묶음을 받는 커널을
  만든다. 입력을 opaque 값으로 넣어 매번 같은 커널이 재생되게 한다.
- 로봇 자신을 건너뛰어야 한다(바퀴 아래로 쏜 광선이 바퀴에 맞는다). 맞은 도형 id가 `body_`로 시작하면 그 뒤에서 다시 쏜다.
- 맞은 도형의 재질 이름을 함께 돌려준다. 씬 XML의 도형마다 재질 이름이 주석(`opticalnav-obj`의 `material`)으로 있다.
  **확인 필요**: 로드할 때 같은 재질의 메시가 합쳐지므로(CS02: 4,965개 → 202개), 합쳐진 뒤에도 재질 이름을 되찾을 수 있는지.
- 물체가 든 씬과 없는 씬이 서로 다른 resident라서, 조회는 뷰와 같은 물체 구성으로 보내야 씬을 다시 로드하지 않는다(지금
  `floor_height`가 쓰는 방식).

### M4b 지면 추종
- 틱마다 바퀴 중심에서 아래로 광선 4개(+ 발자국 모서리 4개)를 쏜다. 접지점 네 개에 평면을 맞춰 베이스의 z, 롤, 피치를 정한다.
- 서스펜션은 없다(강체). 턱이 바퀴 반지름의 일정 비율보다 높으면 "넘지 못함"으로 충돌 처리한다.
- 스폰도 같은 방식으로 한다: 지정한 (x, y)에서 지면을 찾아 그 위에 세운다. `.blend` 씬의 묻힌 시작지점 문제가 함께 풀린다.

### M4c 충돌
- **높이맵**: 씬의 xy 범위(조감도와 같은 범위)를 격자로 나눠, 로봇 최고 높이(마스트 포함 약 1.3 m) 위에서 아래로 광선을 쏜다.
  칸마다 "가장 높은 면의 높이"를 저장한다. 바닥보다 턱 높이 이상 높은 칸이 장애물이다. 테이블 밑처럼 위가 막힌 공간은 막힌 것으로
  본다(마스트가 걸리므로 맞는 판정이다. 마스트 없는 로봇은 낮은 높이에서 한 번 더 쏜 맵을 쓴다).
- 씬당 한 번 만들고 팩에 저장한다(`map/heightmap.npz`). CS02 크기(32 × 32 m)를 5 cm로 하면 41만 칸이다.
- **판정**: 다음 포즈의 발자국 사각형이 막힌 칸과 겹치면 그 이동을 하지 않는다(속도를 0으로). 벽을 따라 미끄러지는 처리는 하지 않는다.
  M4e에서는 같은 맵이 접촉 판정으로 쓰인다.
- 움직이는 문, 다른 로봇 같은 동적 장애물은 다루지 않는다.

### M4d 뷰어 연동
- 지금 뷰어(`gui.py`의 `Session`)는 MatterSim 시뮬레이터 하나와 자유 비행 카메라를 다룬다. 여기에 `SimWorld`를 쓰는 "로봇 세션"을
  나란히 둔다. 기존 세션은 건드리지 않는다.
- 조작: W/S 전후, A/D 조향, Q/E 횡이동, 주행 모드 버튼(Ackermann, 대각, 제자리 회전, 횡이동). 키를 놓으면 감속해서 멈춘다.
- 화면: 리그 카메라마다 창 하나(ISP 영상 / raw / S0 / DoLP / AoLP 선택), 3인칭 추적 카메라 창, 노출·게인 표시.
- 지도: 로봇 발자국과 진행 방향, 지나온 궤적(실제 위치와 오도메트리를 따로), 막힌 영역.
- 시간: 서버가 틱(dt 0.05 s)마다 운동학을 적분하고, 렌더가 끝나는 대로 최신 포즈로 다음 프레임을 요청한다. 멈추면 지금처럼 spp를
  누적한다.
- 하드웨어 구성은 처음에는 "Ranger + 두 대 리그" 프리셋 하나로 고정한다. 구성 편집 화면은 뒤로 미룬다.

### M4e 마찰과 바퀴 동역학
**마찰 계수 지도**
- 재질 이름 → 마찰 계수 표를 둔다(예: 에폭시 바닥 0.6, 타일 0.5, 젖은 타일 0.25, 카펫 0.9, 아스팔트 0.8, 잔디 0.45, 얼음 0.1).
  씬의 재질 이름에서 키워드로 찾고, 못 찾으면 기본값(0.6)을 쓴다. 표의 값은 문헌의 대표값으로 시작한다.
- 사용자가 덮어쓴다: `world.set_friction(material="Gray speckled epoxy floor", mu=0.3)` 또는 영역(다각형)에 값 지정. 젖은 구역,
  기름 자국 같은 실험 조건을 만든다.
- 틱마다 바퀴 접지점의 재질을 M4a로 조회하므로 바퀴 네 개가 서로 다른 마찰 계수를 가질 수 있다.

**동역학 모델 (자체 구현, 평면 강체)**
- 상태: 베이스의 위치·방위와 속도(vx, vy, ω), 바퀴 4개의 각속도와 조향각.
- 바퀴마다: 수직 하중 N(정적 분배, 가감속 시 하중 이동은 옵션), 접지면에서의 미끄럼 속도로 타이어 힘을 계산하고 마찰원
  `|F| ≤ μN`으로 포화시킨다(선형 강성 + 포화로 시작, 필요하면 브러시 모델).
- 구동: 허브 모터는 속도 제어(PI) + 토크 한계. 조향은 지금의 각속도 한계.
- 적분은 1 kHz 부분 스텝. numpy로 충분하다(바퀴 4개).
- 출력: 실제 포즈와 **바퀴 엔코더 오도메트리를 따로** 낸다. 미끄러지면 둘이 벌어진다. 내비게이션 연구에서 필요한 것이 이 차이다.
- 필요한 값: 로봇 질량과 무게중심 높이, 바퀴 관성, 모터 토크 한계, 타이어 강성. 지금은 추정값이다(URDF의 질량 값은 임시값으로
  보인다: 본체 10 kg, 바퀴 8 kg). 제조사 값이나 실측이 필요하다.

**검증 (해석해와 비교)**
1. 마찰이 충분할 때 지금의 운동학 모델과 같은 궤적(기존 테스트 통과).
2. 제동 거리 = v² / (2μg).
3. 정상 선회에서 횡가속도 v²/R이 μg를 넘으면 바깥으로 밀림.
4. 좌우 바퀴의 μ가 다를 때 직진 제동에서 요 회전이 생김.

**하지 않는 것**: 3차원 접촉(턱 넘기, 전복), 서스펜션, 타이어 변형. 필요해지면 MuJoCo 연동(M7)으로 넘긴다. 같은 마찰 지도를
MuJoCo의 geom 마찰로 넘길 수 있게 지도 형식을 정한다.

## 1. 목표

지금의 시뮬레이터는 "카메라 하나가 씬 안을 떠다니는" 구조다. 이것을 Isaac Sim, MuJoCo, CARLA처럼 **실제 하드웨어를 본뜬 장비를
파이썬으로 정의하고, 서로 고정하고, 움직이게 하는 플랫폼**으로 올린다.

1. 로봇, 카메라, 깊이 센서 같은 하드웨어를 파이썬 클래스로 정의한다(CARLA의 blueprint + attach 방식).
2. 하드웨어를 다른 하드웨어 위에 고정한다. 베이스가 움직이면 붙어 있는 것이 모두 따라 움직인다.
3. 로봇이 씬 안에 실제로 보인다(그림자, 거울 반사, 편광 포함). 로봇이 움직이면 Mitsuba 씬 상태가 갱신되되, 가속 구조를 다시
   만들지 않는다.
4. 카메라는 센서 + 렌즈 조합으로 모델링한다. intrinsic과 distortion으로 광선을 만들고, 센서 모델로 raw 값을 만들고, 소프트웨어
   ISP로 실제 카메라가 내는 것과 같은 이미지를 낸다.
5. 센서는 풀 해상도를 지원하되, 기본값은 해상도를 낮춰 렌더한다.

**v1에서 하지 않는 것**: 3차원 접촉을 푸는 강체 물리 엔진, 매니퓰레이터, 변형체. 바퀴의 마찰과 미끄럼은 평면 동역학으로 다룬다
(M4 확장 계획의 M4e). 3차원 물리가 필요하면 MuJoCo를 뒤에 붙인다(8절 M7).

걸리는 것도 코드에서 확인했다.
- 서버의 한 뷰 한도가 `MAX_PIXELS = 2048 × 2048`(4.19 MP)이다. TDR054S 풀 해상도(5.36 MP)는 이 한도를 넘는다.
- Mitsuba 3.9.1의 `perspective` 센서는 주점 오프셋만 받고 왜곡 계수는 없다. 센서 플러그인은 `perspective`, `thinlens`, `batch` 등뿐이다.
- 뷰의 카메라는 `hfov_deg` 하나로 정해진다. fx ≠ fy, 주점, 왜곡을 넣을 자리가 프로토콜에 없다.

## 3. 구조

네 층으로 나눈다. 위 두 층은 GPU가 필요 없는 순수 파이썬이라 테스트가 쉽다.

```
[A] opticalnav_sim.hw      하드웨어 정의: World, Actor, Transform 트리, 로봇·카메라·렌즈·센서 명세, 운동학
[B] 센서 모델 + ISP         장면 복사휘도(Stokes) -> 센서 전자 -> raw DN -> ISP 이미지
[C] 씬 동기화 프로토콜       tick마다 "링크 포즈 목록 + 센서 목록"을 서버로 보낸다
[D] 렌더러                  동적 물체(shapegroup + instance), 왜곡 카메라 광선, 세 백엔드
```

### 3.1 파이썬 API (CARLA 식)

```python
import opticalnav_sim as ons
from opticalnav_sim import hw

world = ons.World("http://127.0.0.1:18770", scene="blend_REF_PH46", dt=0.05)

robot = world.spawn(hw.robots.RangerMini2(), at=world.spawn_points()[0])

cam = world.spawn(
    hw.cameras.LucidTDR054S(lens=hw.lenses.FujinonHF6XA5M(f_number=4.0), render_scale=0.25),
    attach_to=robot,
    mount=hw.Transform(xyz=(0.25, 0.0, 0.45), rpy_deg=(0.0, 8.0, 0.0)))     # base_link 기준, ROS 축
polcam = world.spawn(hw.cameras.FlirBFS51S5PC(lens=hw.lenses.FujinonHF6XA5M()), attach_to=robot, mount=...)
depth = world.spawn(hw.sensors.DepthCamera(width=640, height=480, hfov_deg=87.0), attach_to=cam, mount=...)

robot.apply_control(hw.RangerControl(mode="ackermann", linear=0.5, steering_deg=10.0))
world.tick()                      # 운동학 적분 -> 트리 포즈 갱신 -> 서버에 포즈와 센서 전달 -> 렌더

f = cam.read()
f.raw          # Bayer DN (uint16 / uint32), 실제 카메라의 raw와 같은 형식
f.image        # ISP를 거친 8-bit RGB
f.stokes       # 정답 Stokes (옵션, 실제 카메라에는 없는 값)
f.intrinsics   # 렌더 해상도 기준 K, 왜곡 계수
f.pose         # world 기준 4x4, 타임스탬프
```

정한 것:
- **좌표계**: 하드웨어 정의는 ROS REP-103(x 앞, y 왼쪽, z 위)으로 쓴다. 시뮬레이터 내부 좌표(Mitsuba y-up, R2R)로의 변환은
  `frames.py` 한 곳에서만 한다.
- **명세는 데이터**: 카메라, 렌즈, 로봇은 dataclass다. 새 하드웨어는 값을 채운 클래스 하나를 등록하면 된다. 실측 캘리브레이션
  (OpenCV / Kalibr YAML)을 읽어 데이터시트 기본값을 덮어쓸 수 있다.
- **로봇은 URDF에서**: 링크, 조인트, 메시를 URDF로 읽는다. 다른 로봇을 추가하는 길이 된다.
- **MatterSim API는 유지**: 기존 `Simulator`는 "가상 리그 하나를 가진 World"로 감싼다. 기존 학습 코드는 그대로 돈다.

### 3.2 시간

- `World`는 고정 `dt`로 진행한다(CARLA의 synchronous mode). 센서마다 `fps`가 있고, 주기가 된 센서만 그 tick에 렌더한다.
- 같은 tick에 같은 해상도인 센서는 batch 센서로 한 번에 렌더한다.
- 기존 spp 정책을 따른다. 움직이는 동안은 적은 spp + 디노이즈, 멈추면 누적.

## 4. 로봇이 씬에 보이고 움직이게 하기 (가장 큰 기술 위험)

### 4.1 방법

- 로봇 = 강체 링크 N개(섀시, 조향 모듈 4, 바퀴 4, 센서 마스트, 카메라 몸체: 10~15개).
- 링크 하나 = `shapegroup`(씬 로드 때 한 번 만들고 다시 만들지 않는다) + `instance`(`to_world`만 바뀐다).
- tick마다 N개의 4x4를 쓴다. 다시 만들어지는 것은 인스턴스를 담는 최상위 구조뿐이고, 씬의 메시 BVH와 링크의 BVH는 그대로다.
- 변환은 지금 플래시가 하듯 opaque 값으로 써서 frozen 커널을 다시 녹화하지 않는다.
- 로봇 모델은 "숨김 풀"처럼 씬 로드 때 함께 올려 두고(주차 위치), 스폰하면 꺼낸다. 로드 뒤에 새 모델을 넣으려면 씬을 다시 로드해야 하므로,
  에피소드 시작 때 쓸 하드웨어 목록을 정한다.

### 4.2 아직 모르는 것 (S1에서 측정)

- 인스턴스 10~15개의 `to_world`를 쓰고 `parameters_changed`를 부르는 비용. 목표는 프레임당 5 ms 이하.
- frozen 재생이 인스턴스 변환을 입력으로 받아 재녹화 없이 도는지. 플래시(사각형)에서는 됐지만 인스턴스에서는 해 보지 않았다.
- 이전에 측정한 "최상위 도형·인스턴스 수가 늘면 녹화 시간과 RAM이 는다"는 문제. 링크 15개는 작지만 확인한다.
- **대안**: 인스턴스가 안 되면 링크를 일반 메시로 두고 정점을 GPU에서 변환해 쓴다(그 메시의 가속 구조만 다시 만든다. 지금 조명
  사각형이 PLY로 바뀌어 이렇게 움직인다).

### 4.3 세부

- **자기 몸이 보이는 문제**: 카메라가 자기 하우징 안에 있으면 검은 화면이 된다. 링크마다 `visible_to_own_sensors`를 두고, 꺼진 링크는
  기존 `hidden` 접두사(카메라 광선 통과)로 처리한다. 로봇의 그림자와 거울 속 모습은 그대로 남는다. 이것이 의도한 사실성이다.
- **재질**: 로봇 메시의 재질은 `.blend` 변환기의 재질 매핑(pplastic / roughconductor / dielectric)을 그대로 쓴다. 아노다이징
  알루미늄, 고무 타이어, 도장 철판이 편광까지 맞게 나온다.
- **백엔드별**: Cycles는 Blender 씬에 링크 오브젝트를 넣고 `matrix_world`만 바꾸면 된다(쉬움). 래스터는 동적 메시 지원이 필요하다
  (래스터는 다른 사람이 작업 중이라 조율이 필요하다).

### 6.2 카메라 파이프라인

장면에서 이미지까지 다섯 단계다. 각 단계를 끄거나 바꿀 수 있다.

1. **광선 (intrinsic + distortion)**: `fx, fy, cx, cy`와 OpenCV 왜곡 계수(`k1, k2, p1, p2, k3`, 어안은 Kannala-Brandt)로 픽셀의
   광선을 만든다. 구현은 두 가지다.
   - (가) 조금 넓은 화각의 핀홀로 렌더한 뒤 왜곡 맵으로 다시 샘플링한다. 세 백엔드 모두에서 되고 바로 만들 수 있다. 왜곡 −2.85%에서는
     여유 화각이 3~6%면 된다. 리샘플링으로 약간 흐려진다.
   - (나) Mitsuba에 왜곡 센서 플러그인을 추가한다. 픽셀별로 정확한 광선을 쏘므로 흐려짐이 없다.
   - **(가)를 먼저 하고, 정확도가 필요해지면 (나)를 Mitsuba용 "정확 모드"로 추가한다.**
2. **렌즈**: 비네팅(cos⁴ + 렌즈의 주변 광량 곡선), PSF 흐림(MTF에서 유도), 투과율. 색수차와 피사계 심도는 옵션이다. 6 mm F4에서
   과초점 거리는 약 1.5 m라서 0.75 m 밖은 모두 선명하다. 그래서 기본은 핀홀이다. 플레어와 고스트는 하지 않는다.
3. **편광 → 세기**: 시뮬레이터가 Stokes를 내므로 이 단계가 정확하다.
   - 일반 카메라: 세기 = S0.
   - 편광 필터를 단 카메라, 편광 센서: `I(θ) = ½[(t_max + t_min)·S0 + (t_max − t_min)(S1 cos2θ + S2 sin2θ)]`. 소광비가 유한한 것을
     `t_max, t_min`으로 넣는다.
   - 주의: 서버의 Stokes 기준축은 `world_gravity_y_v1`이다. 센서 축 기준으로 픽셀마다 돌려야 한다.
4. **센서**: 복사휘도 → 센서면 조도(`E = π/4 · L · T / N²`) → 광자 → 전자(QE) → 잡음(샷, 읽기, 암전류, PRNU/DSNU) → 게인 →
   블랙 레벨 → ADC 양자화. 값은 제조사의 EMVA 1288 자료에서 가져온다(아직 수집하지 않았다).
   - 분광: 시뮬레이터의 R, G, B, NIR 네 밴드에서 카메라 채널로 가는 행렬로 근사한다. IR 차단 필터 유무를 명세에 둔다.
   - **TDR054S (IMX490)**: 한 픽셀의 큰·작은 포토다이오드 × 두 게인, 네 판독을 합쳐 24-bit 선형을 만든다. 합성 경계에서 SNR이
     떨어지는 것까지 모델링한다.
   - **TRI032S**: Bayer RGGB, 12-bit.
   - **FLIR 51S5PC**: 2×2 편광(0/45/90/135°) 블록이 다시 Bayer로 배열된 4×4 모자이크.
5. **ISP (소프트웨어)**: 블랙 레벨 → 불량 화소 → 렌즈 셰이딩 보정 → 디모자이크 → 화이트 밸런스 → 색 보정 행렬 → 톤(감마 / LUT /
   HDR 톤매핑) → 샤픈·디노이즈 → 출력 형식(Mono8, BayerRG8/12/16/24, RGB8).
   - 편광 카메라는 편광 디모자이크 → 4방향 영상 → S0, S1, S2 → DoLP / AoLP까지 낸다. 시뮬레이터의 정답 Stokes와 바로 비교할 수 있다.
   - TDR054S의 카메라 내 톤매핑(AltaView)은 비공개라 똑같이 만들 수 없다. 전역 + 국소 톤매핑으로 근사하고 사용자 LUT를 받는다.
   - 구현은 torch(GPU), numpy 대체 경로. 자동 노출(AE)과 자동 화이트 밸런스는 프레임 사이의 루프로 흉내 낸다.

### 6.3 해상도 정책

- 명세에는 풀 해상도를 적고, `render_scale`(기본 0.25)로 낮춰 렌더한다. TDR054S는 720 × 465가 된다.
- 실제 카메라의 기능 이름을 그대로 쓴다: `binning`, `decimation`, `roi`. intrinsic은 자동으로 따라 바뀐다.
- 낮춘 해상도에서 잡음을 어떻게 볼지는 모드로 둔다. 비닝(k² 픽셀 평균, SNR 상승)과 데시메이션(픽셀 건너뛰기, SNR 유지).
- 낮춘 해상도의 Bayer / 편광 모자이크는 "그 해상도의 가상 센서"다. 디모자이크 아티팩트의 크기가 실제와 달라진다. 최종 데이터는 풀
  해상도로 뽑는다.
- 풀 해상도 비용: 5.36 MP는 지금 기본(512 × 384)의 약 27배 픽셀이다. 1024 spp에서 프레임당 분 단위가 될 것으로 본다(S4에서 측정).
  서버의 `MAX_PIXELS` 한도를 올리거나 타일로 나눠 렌더해야 한다.

### 6.4 그 밖의 센서

- **깊이 카메라**: 광선 깊이(이미 있음) + 잡음 모델(거리 제곱에 비례하는 축 방향 잡음, 유리·거울에서의 무효 픽셀).
- **LiDAR**: 같은 광선 커널로 2D / 3D 스캔.
- **IMU, 휠 엔코더, 오도메트리**: 운동학에서 나온다.
- **정답 센서**: 시맨틱 / 인스턴스 ID, 법선, 정답 Stokes.

## 7. 프로토콜 변경

- 뷰에 `sensor`를 추가한다: `{model: "opencv", fx, fy, cx, cy, dist: [...], width, height}`. `hfov_deg`는 호환용으로 남긴다.
- 뷰에 `bodies`를 추가한다: `[{id, model, links: {이름: 4x4}}]`.
- `GET /v1/hardware`: 서버가 가진 하드웨어 모델 목록. 씬 로드 요청에 "이 에피소드에 쓸 모델"을 넣는다.
- 하드웨어 팩: `packs/hardware/<model>/`에 링크 메시(PLY), 재질, `model.json`(링크 트리, 치수).
- 센서 모델과 ISP는 클라이언트(`hw`)에서 돌린다. 서버는 지금처럼 Stokes / 복사휘도를 낸다. 서버 쪽 변경이 작고, 한 렌더에서 ISP
  설정만 바꿔 다시 뽑을 수 있다.

## 8. 단계

먼저 위험을 재는 스파이크(각 1~2일)를 하고, 그 결과로 뒤 단계의 방법을 확정한다.

| | 내용 | 통과 기준 |
|---|---|---|
| **S1** | 인스턴스 15개를 매 프레임 움직이기 | 갱신 5 ms 이하, frozen 재녹화 없음. 안 되면 정점 쓰기 대안으로 |
| **S2** | 왜곡: 핀홀 + 리맵 정확도와 비용 | OpenCV `projectPoints` 대비 재투영 오차 0.1 px 이하 |
| **S3** | Ranger Mini 2.0 URDF·메시 확보와 변환 | 메시가 팩으로 변환되고 치수가 공식 값과 맞음 |
| **S4** | 풀 해상도 렌더(5.36 MP) | 메모리와 시간 측정, 타일 필요 여부 결정 |

| | 내용 | 통과 기준 | 크기 |
|---|---|---|---|
| **M1** | `hw` 코어: Transform 트리, World / Actor, 등록, attach, 좌표 변환. MatterSim 호환 | 순수 파이썬 단위 테스트. 기존 테스트 43개 유지 | 작음 |
| **M2** | 카메라 명세 + 렌즈 intrinsic / 왜곡 + `render_scale`. 카메라 3종과 렌즈 blueprint | S2 기준. 뷰어에서 카메라 모델 선택 | 중간 |
| **M3** | Mitsuba 동적 물체: Ranger가 보이고 움직임 | S1 기준. "로봇을 그 포즈로 구운 씬"과의 차이가 잡음 이내 | 중간~큼 |
| **M4** | Ranger 운동학 + 제어 API + 지면 추종 + 충돌. 뷰어에서 로봇 조종, 지도에 로봇 표시 | 네 주행 모드의 궤적이 해석해와 일치 | 중간 |
| **M5** | 센서 복사 측정 + 잡음 + ISP. 편광 카메라 포함 | 시뮬레이션의 photon transfer curve가 EMVA 자료와 일치. 편광 카메라의 DoLP / AoLP가 정답 Stokes와 일치(잡음 없을 때 0.01 이내) | 큼 |
| **M6** | 깊이 잡음, LiDAR, IMU / 오도메트리. Cycles·래스터의 로봇 표시. ROS 2 브리지 | 실제 로봇용 ROS 노드가 수정 없이 시뮬레이터에 붙음 | 큼 |
| **M7** | 옵션: MuJoCo 물리 연동, 롤링 셔터, 모션 블러 | 필요할 때 | |

- **M6의 ROS 2 브리지**가 "실제 장비를 시뮬레이터에 deploy한다"의 핵심이다. `Image`, `CameraInfo`, `tf`, `odom`을 내고 `cmd_vel`을
  받아서, 실제 로봇에서 도는 스택이 인터페이스 차이 없이 시뮬레이터에 붙는다.
- **M7의 MuJoCo**: 물리는 MuJoCo가 풀고 렌더는 우리 것이 한다. `hw` 트리는 링크 포즈만 받으면 되므로 구조를 바꾸지 않고 붙는다.
- **실물 검증(M5)**: 실제 카메라로 찍은 컬러 체커, 균일 조명, 체커보드가 있으면 센서 값과 왜곡 계수를 실측에 맞춘다. 없으면
  데이터시트 값으로 출발한다.

## 9. 위험

| 위험 | 영향 | 대응 |
|---|---|---|
| 인스턴스 갱신이 frozen 재녹화를 부른다 | 로봇이 움직일 때마다 수십 초 멈춤 | S1에서 먼저 측정. 정점 쓰기 대안 |
| 풀 해상도가 GPU 메모리를 넘는다 | 최종 데이터 렌더 불가 | 타일 렌더. 기본은 낮춘 해상도 |
| 절대 복사량 단위가 씬마다 다르다 | 노출·잡음 모델이 의미를 잃는다 | 씬마다 기준 조도(lux)를 정해 스케일을 맞춘다 |
| R, G, B, NIR 네 밴드로는 분광 응답이 거칠다 | 색 재현과 NIR 누설 오차 | 행렬 근사로 출발. 컬러 체커 실측으로 맞춘다 |
| 카메라 내 ISP(AltaView)가 비공개다 | 8-bit 출력이 실물과 다르다 | raw 24-bit 경로를 기준으로 삼고 톤매핑은 근사 |
| 래스터 백엔드는 다른 사람이 작업 중이다 | 로봇 표시가 래스터에서 늦어진다 | Mitsuba 먼저. 래스터는 조율 뒤 |
| 로봇 사양 일부가 2차 출처뿐이다 | 운동학 치수 오차 | 공식 매뉴얼 / URDF로 확인(S3) |

## 10. 정해야 할 것

괄호 안이 기본안이다. 답이 없으면 기본안으로 간다.

1. 후지 6 mm 렌즈의 정확한 모델(HF6XA-5M으로 가정). 실측 캘리브레이션(intrinsic, 왜곡)이 있는지.
2. FLIR 컬러 편광 카메라의 정확한 모델(BFS-U3-51S5PC-C로 가정).
3. 물리 수준(운동학으로 시작, MuJoCo는 나중).
4. 인터페이스(파이썬 API 먼저, ROS 2 브리지는 M6).
5. TDR054S는 어느 출력을 흉내 낼지(raw 24-bit + 우리 ISP를 기준으로, 8-bit 톤매핑은 근사).
6. 검증용 실물 촬영 데이터를 줄 수 있는지.
7. 카메라와 센서를 로봇의 어디에 다는지(마운트 위치와 각도. 실제 리그의 치수가 있으면 그것을 기본 blueprint로 넣는다).
